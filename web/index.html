The situation

Messy formats

Invoices arrive as text emails, PDFs, CSV, JSON and XML. Some have OCR slips, typos or repeated lines. Today staff retype them by hand.

Approval limit

Large invoices need extra scrutiny before anyone pays them.

Fraud risk

Some invoices push urgency, ask for a wire to a new account, come from vendors not on file or sit just under the limit.

Inventory to check

Every line has to match the inventory database: the item must exist and there must be enough stock.

From the Galatiq case brief: manual processing costs Acme about $2M a year, 30% of invoices carry an error and payment takes 5 days.

What is in the inbox

    How Grok will handle each one

    1. 1. IngestRead the file and pull out vendor, items, amounts and dates. A format parser runs first; Grok extracts only what the parser cannot read, and its answer is checked against a schema.
    2. 2. ValidateCode checks each line against inventory, redoes the math, checks dates, currency, prices, vendor and duplicates. Any blocking flag means the invoice cannot be paid.
    3. 3. RiskWeighted fraud signals give a score from 0 to 100. On invoices with no blocking flag, Grok calls read-only tools (vendor master, inventory, vendor history) and can raise the score with reasons, never lower it.
    4. 4. VP approvalA VP agent reads the flags and the risk review and proposes approve, hold or reject, with reasons and conditions.
    5. 5. CriticA critic challenges VP approvals that are large, near the limit or high risk.
    6. 6. OutcomePay through the mock bank (once, with an idempotency key), reject with reasons logged, or hold in a review queue for a human.

    What each status means

    Approved
    Checks passed and the VP approved, so it was paid.
    Rejected
    A hard rule failed (stock, math, duplicate, missing data) or the VP rejected it. Not paid; reasons logged.
    Held for a human
    Something needs a person to confirm before money moves. It waits in the review queue with the reasons attached.
